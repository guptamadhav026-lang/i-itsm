## 1. The big picture

The backend is a **layered architecture**. Each layer only talks to the layer below it.

```
 Frontend (React or Thymeleaf, decided later)  /  Swagger UI  /  tests
                     │  HTTP + JSON, "Authorization: Bearer <token>"
                     ▼
 ┌───────────────────────────────────────────────────────────────┐
 │ web/          Controllers: receive requests, check the role,   │
 │               turn entities into DTOs (JSON)                   │
 ├───────────────────────────────────────────────────────────────┤
 │ service/      Business logic: the incident workflow, SLA       │
 │               monitor, search, reports, users, catalog         │
 │   uses ──►    strategy/  intelligence/  event/  notification/  │
 ├───────────────────────────────────────────────────────────────┤
 │ model/        Domain objects with their own rules              │
 │               (Incident refuses illegal status changes, etc.)  │
 ├───────────────────────────────────────────────────────────────┤
 │ repository/   Database access (Spring Data JPA)                │
 └───────────────────────────────────────────────────────────────┘
                     │  SQL (generated by Hibernate)
                     ▼
              H2 file database (default) or PostgreSQL
```

Why layers? Each layer has one job, so a change in one place (e.g. switching H2 to PostgreSQL, or React
to Thymeleaf) does not ripple through the rest. This is the "separation of concerns" the brief asks you
to justify under *architecture*.

## 2. Follow one incident through the code

John (an employee) reports *"Office wifi not working"*. Here is exactly what happens, file by file.

| Step | What happens | Where |
|---|---|---|
| 0 | John logs in. His password is checked against the BCrypt hash and he gets a signed JWT token. | `AuthService.login`, `JwtService.issue` |
| 1 | The frontend sends `POST /api/incidents` with the token and JSON body. Spring checks the token and the role (`EMPLOYEE` or `ADMIN`). The JSON is validated (`@NotBlank`, `@Min(1)`...). | `SecurityConfig`, `IncidentController.create`, `CreateIncidentRequest` |
| 2 | **Create**: a new `Incident` object is built. Its constructor refuses a blank title or 0 affected users. Status starts as `NEW`. Saved to the database. Event `CREATED` is published. | `IncidentService.create`, `Incident` constructor |
| 3 | **Classify**: no category was chosen, so the categoriser scans the text for category keywords. "wifi" is a NETWORK keyword → NETWORK. Status `NEW → CLASSIFIED` (the State object allows it). | `IncidentCategorizer.suggest`, `Incident.classify`, `NewState` |
| 4 | **Prioritise**: the active priority strategy computes `Impact × Urgency × Business criticality × Users factor` = 2 × 3 × 4 × 1.25 = 30 → **P2**. The explanation text is stored. | `WeightedPriorityStrategy.assess` |
| 5 | **SLA**: the P2 policy is loaded from the database (respond in 15 min, resolve in 2 h) and both deadlines are stored on the incident. | `SlaService.applyDeadlines` |
| 6 | **Duplicates**: recent open incidents are compared by text similarity. If one scores ≥ 0.45 the incident is flagged as a possible duplicate. | `DuplicateDetector.findSimilar` |
| 7 | **Assign**: available technicians below their workload limit become candidates. The SMART strategy scores each (skill, experience, history, workload) and picks Alice. Status `CLASSIFIED → ASSIGNED`. | `IncidentService.tryAutoAssign`, `SmartAssignmentStrategy` |
| 8 | **Notify + audit**: every step above published an `IncidentEvent`. The audit listener writes an `AuditRecord`; the notification listener decides who to tell (Alice, John) and through which channels (in-app always, email too for P1/P2). | `IncidentEventPublisher`, `AuditTrailListener`, `NotificationEventListener`, `NotificationChannelFactory` |
| 9 | The controller turns the `Incident` into an `IncidentDetailDto` (adds live SLA state and the allowed next statuses) and returns JSON with HTTP 201. | `IncidentViews`, `IncidentDetailDto` |
| 10 | Alice acknowledges, starts the investigation, asks John a question, John answers, Alice resolves. Each call goes through the State pattern; anything out of order gets HTTP 409. | `IncidentService.acknowledge/startInvestigation/requestInformation/resolve` |
| 11 | Meanwhile, every minute, the SLA monitor checks all open incidents: warnings at 75%, breaches after deadlines, escalation of unacknowledged P1/P2. | `SlaMonitorScheduler`, `SlaMonitorService` |
| 12 | John verifies and closes it, then rates it 5/5. The incident now counts in the reports. | `IncidentService.verify/close/giveFeedback`, `ReportService` |

The automated test `IncidentApiTest.fullWorkflow` (TC26) runs exactly this story.

## 3. Package tour

All code is under `src/main/java/com/itsm`.

### `ItsmApplication.java`
The `main` method. `@SpringBootApplication` starts Spring, which finds every class marked `@Service`,
`@Component`, `@RestController`... creates one object of each and connects them. `@EnableScheduling`
turns on the SLA monitor timer.

### `model/` – the domain
| Class | What it is |
|---|---|
| `User` (abstract) | Common fields: username, password hash, name, email, active. Abstract methods `getRole()` and `canView(Incident)`. |
| `Employee`, `Technician`, `Administrator` | The three kinds of user. Technician adds skills, experience, max workload, availability, team-lead flag. Administrator adds the IT-manager flag. |
| `Incident` | The central object. Holds all incident data and has methods for every lifecycle step. **No setter for status**: only `classify()`, `assignTo()`, `acknowledge()`... and each one asks the State object first. |
| `IncidentNote` | Investigation notes, info requests/answers and comments. Owned by an incident (composition). |
| `ItService` | A business service (Payment Gateway, Email...) with a business criticality 1–5. |
| `Category` | NETWORK, HARDWARE... with keywords used for auto-categorisation. Stored in the database so admins can add new ones. |
| `SlaPolicy` | Response and resolution minutes for one priority, plus the warning threshold. |
| `AuditRecord` | One line of history. Immutable: no setters at all. |
| `Notification` | One message delivered to a user on one channel. |
| Enums | `Priority` (P1–P4 with default SLA times), `IncidentStatus`, `Impact`, `Urgency`, `Role`, `EscalationLevel`, `NoteType`, `SlaState`, `NotificationChannelType`. |

### `model/state/` – State pattern
`IncidentState` interface + one class per status (`NewState`, `ClassifiedState`, ..., `ClosedState`).
Each says which statuses may come next. `IncidentStateFactory` hands out the right one.

### `strategy/` – Strategy pattern
* `priority/`: `PriorityStrategy` interface, `WeightedPriorityStrategy`, `ItilMatrixPriorityStrategy`.
* `assignment/`: `AssignmentStrategy` interface, `SkillBasedAssignmentStrategy`, `LoadBasedAssignmentStrategy`,
  `RoundRobinAssignmentStrategy`, `SmartAssignmentStrategy`.
* `StrategyRegistry<T>`: a **generic** class that keeps all strategies of one kind and remembers which is
  active, so an admin can switch at runtime.

### `event/` – Observer pattern
`IncidentEvent` (what happened), `IncidentEventPublisher` (the subject), `IncidentEventListener` interface
with two observers: `AuditTrailListener` and `NotificationEventListener`.

### `notification/`
`NotificationChannel` interface, `InAppNotificationChannel`, `EmailNotificationChannel` (simulated: it logs
the email and stores it), `NotificationChannelFactory`, `NotificationService`.

### `intelligence/`
`TextAnalyzer` (keywords, synonyms, Jaccard similarity), `DuplicateDetector`, `IncidentCorrelator`,
`IncidentCategorizer`, `ResolutionSuggester`, `SlaRiskAnalyzer`, and small result records.

### `service/` – business logic
| Class | Job |
|---|---|
| `IncidentService` | The whole incident workflow and permission checks. The most important file. |
| `SlaService` | Which SLA applies, deadlines, how much time is used, SLA state. |
| `SlaMonitorService` + `SlaMonitorScheduler` | Background check every minute: warnings, breaches, escalation. |
| `UserService`, `UserFactory`, `AuthService` | Accounts, creating the right user subclass, login. |
| `SearchService` + `IncidentSearchCriteria` | Search with 11 optional criteria. |
| `ReportService` | Overview, workload, per-service and per-category reports, SLA risk, correlations. |
| `CatalogService` | Admin management of services, categories, SLA policies. |
| `AuditService` | Reads the audit trail. |

### `repository/`
Interfaces like `IncidentRepository extends JpaRepository<Incident, Long>`. You write only the method
*name* (`findByReporterOrderByCreatedAtDesc`) and Spring writes the SQL.

### `web/`
Controllers (`AuthController`, `IncidentController`, `CatalogController`, `AdminController`,
`TechnicianController`, `ReportController`, `NotificationController`), `GlobalExceptionHandler`,
`IncidentViews`, and `dto/` (request and response records). DTOs keep the API stable and never expose
password hashes.

### `security/` and `config/`
`JwtService` (creates tokens), `CurrentUser` (token → User), `SecurityConfig` (rules, BCrypt, JWT),
`ClockConfig` (one shared clock so tests can fast-forward time), `OpenApiConfig` (Swagger),
`DataSeeder` (demo data).

### `exception/`
`ItsmException` (abstract) and its subclasses. See [section 13](#13-exceptions).

## 4. OOP concepts and where to find them

| Concept | Where | What to say |
|---|---|---|
| **Encapsulation** | `Incident` | Fields are private. There is no `setStatus()`: status changes only through `acknowledge()`, `resolve()`... which validate first. `getNotes()` returns a read-only list. |
| | `Technician.getSkills()` | Returns a copy so outside code cannot change skills behind the object's back. |
| | `AuditRecord` | Immutable: all fields set in the constructor, no setters. History can't be rewritten. |
| **Abstraction** | `User` (abstract class) | "A user" is an idea; you can only create an Employee, Technician or Administrator. |
| | `PriorityStrategy`, `AssignmentStrategy`, `NotificationChannel`, `IncidentState`, `IncidentEventListener` | Interfaces describe *what*, classes decide *how*. |
| **Inheritance** (true is-a) | `Employee`/`Technician`/`Administrator extends User` | Each really *is a* user. Stored in one table with a `user_type` column (JPA SINGLE_TABLE). |
| | `ResourceNotFoundException extends ItsmException extends RuntimeException` | Exception hierarchy. |
| **Polymorphism** | `user.canView(incident)` in `IncidentService.getVisible` | Same call, different rule: employee only own incidents, technician and admin all. |
| | `strategy.assess(incident)` / `strategy.selectTechnician(...)` | The service doesn't know which strategy runs. |
| | `ex.getStatus()` in `GlobalExceptionHandler` | Each exception type knows its own HTTP status. |
| | `channel.deliver(...)`, `listener.onEvent(...)` | Many implementations behind one interface. |
| **Interfaces** | see Abstraction row | Plus Spring Data repository interfaces. |
| **Composition** | `Incident` ↔ `IncidentNote` | Notes can't exist without their incident (`cascade = ALL, orphanRemoval = true`, package-private constructor). |
| **Association / aggregation** | `Incident` → `User` reporter, `Technician`, `ItService`, `Category` | They exist independently of the incident. |
| **Exception handling** | `exception/`, `GlobalExceptionHandler` | Custom checked business rules, turned into clean JSON errors. |
| **Collections** | `EnumMap` in `IncidentStateFactory` and `NotificationChannelFactory`; `EnumSet` for status groups in `IncidentStatus`; `LinkedHashMap` in `StrategyRegistry`; `Set` for skills; `TreeMap` + `Collectors.groupingBy` in `ReportService` | Chosen for the job: EnumMap is fast and ordered for enum keys, Set prevents duplicate skills... |
| **Generics** | `StrategyRegistry<T extends NamedStrategy>` | One registry class serves both strategy families. |
| **Records** | DTOs, `PriorityAssessment`, `SimilarIncident`... | Short immutable data carriers. |
| **Lambdas / Streams** | `ReportService`, `SearchService`, strategies | Filtering, sorting, grouping. |

## 5. Design patterns

The brief requires two. The code uses five, plus a generic registry.

### 5.1 State – incident lifecycle
* Files: `model/state/*`, `Incident.moveTo()`.
* Each status is a class that knows its allowed next statuses:

```
NEW → CLASSIFIED → ASSIGNED → ACKNOWLEDGED → IN_PROGRESS → RESOLVED → VERIFIED → CLOSED
                     ↑  ↺ reassign  ↑            ↑   ↓reopen
                     └──────────────┴────────────┘
```
* `Incident.moveTo(target)` calls `currentState().validateTransition(target)`, which throws
  `InvalidStateTransitionException` (HTTP 409) for anything illegal, e.g. NEW → CLOSED.
* Why: lifecycle rules live in small classes instead of one giant `if/else`. Adding a state (e.g.
  `ON_HOLD`) means adding one class and one enum value.

### 5.2 Strategy – priority and assignment
* Files: `strategy/priority/*`, `strategy/assignment/*`, `StrategyRegistry`.
* `IncidentService` only calls `priorityStrategies.getActive().assess(incident)`; it never names a concrete strategy.
* Admin can switch with `PUT /api/admin/strategies/assignment {"name":"LOAD_BASED"}`, no restart, no code change.
* Adding a strategy: write one class with `@Component` implementing the interface. Spring finds it and puts it in the registry automatically.

### 5.3 Observer – events, audit and notifications
* Files: `event/*`.
* `IncidentService` publishes events (`CREATED`, `ASSIGNED`, `SLA_VIOLATED`...) and does not know who listens.
* Two observers: `AuditTrailListener` (writes history) and `NotificationEventListener` (tells people).
* One failing listener doesn't stop the others (`IncidentEventPublisher` catches per listener).
* Adding e.g. a Slack/WebSocket listener means one new class, nothing else changes.

### 5.4 Factory – creating the right object
* `UserFactory`: role → `Employee`/`Technician`/`Administrator`.
* `NotificationChannelFactory`: channel type → channel object; `channelsFor(important)` chooses the channels.
* `IncidentStateFactory`: status → state object.

### 5.5 Repository – persistence
* Files: `repository/*`.
* The business code asks `incidents.findByStatusIn(...)` and never writes SQL; switching H2 → PostgreSQL needs no code change.

## 7. The intelligent features

| | Feature | How it works | File |
|---|---|---|---|
| A | **Duplicate detection** | Text is reduced to keywords (lower-case, stop words removed, simple stemming, synonyms like *unavailable/down/outage → failure*, *pay/checkout → payment*). Similarity = 0.6 × title similarity + 0.4 × full-text similarity (+0.15 if same service), using the Jaccard index (shared words ÷ all words). ≥ 0.45 → possible duplicate. | `TextAnalyzer`, `DuplicateDetector` |
| B | **Correlation** | Open incidents from the last 24 h are grouped by service; 2 or more on one service → "possible major incident". | `IncidentCorrelator` |
| C | **Automatic escalation** | P1/P2 not acknowledged after the response deadline: Team Lead → System Administrator → IT Manager, one level per response period. | `SlaMonitorService.checkEscalation`, `NotificationEventListener` |
| D | **Smart recommendation** | Score = skill match 40 + experience (2/yr, max 20; halved for P3/P4) + resolved incidents on the same service (4 each, max 20) + free capacity (max 20). The reasons are shown. | `SmartAssignmentStrategy`, `GET /api/incidents/{id}/recommended-technicians` |
| E | **SLA risk** | Risk 0–100 = 70 × fraction of time used + 15 if not acknowledged + 15 if waiting for the reporter. | `SlaRiskAnalyzer`, `GET /api/reports/sla-risk` |
| F | **Auto-categorisation** | The category whose keywords appear most in the text wins; otherwise GENERAL. | `IncidentCategorizer`, `POST /api/catalog/suggest-category` |
| G | **Suggested resolutions** | Resolved incidents most similar to this one (bonus for same category/service), top 3. | `ResolutionSuggester`, `GET /api/incidents/{id}/suggested-resolutions` |

All are rule-based, explainable, and need no external AI service. A later upgrade could call an AI API
(e.g. for categorisation) behind the same interfaces.

## 8. Priority algorithm and its rationale

```
score = Impact(1–4) × Urgency(1–4) × Business criticality of the service(1–5) × Users factor
Users factor: 1 user → 1.0 · 5+ → 1.1 · 20+ → 1.25 · 100+ → 1.5

score ≥ 40 → P1 Critical      score ≥ 20 → P2 High
score ≥ 8  → P3 Medium        otherwise  → P4 Low
```

Rationale:
* It is the brief's example formula, extended with the number of affected users (also listed in the brief).
* Multiplying means one "low" factor pulls the priority down: a critical problem for one person on a
  low-criticality service is not a P1.
* Thresholds were chosen so that typical cases land where an IT manager would expect:
  payments down for everyone (4×4×5×1.5 = 120) → P1; slow VPN for 25 people (2×3×4×1.25 = 30) → P2;
  one broken laptop (1×1×2×1 = 2) → P4.
* The explanation string stored on every incident shows the calculation, so priorities are auditable.
* The alternative `ITIL_MATRIX` strategy (impact + urgency only) is the classic ITIL table.
  Admins can switch between them.

## 9. SLA, warnings and escalation

Default policies (editable by admins at `PUT /api/admin/sla-policies/{priority}`):

| Priority | Response | Resolution | Warning at |
|---|---|---|---|
| P1 | 5 min | 30 min | 75% |
| P2 | 15 min | 2 h | 75% |
| P3 | 1 h | 8 h | 75% |
| P4 | 4 h | 24 h | 75% |

* **Response** = time until the technician acknowledges. **Resolution** = time until resolved.
* Deadlines are stored on the incident when it is created (and recalculated if the priority changes).
* Every 60 s `SlaMonitorService.runChecks()`:
  1. response deadline passed and not acknowledged → response breach (`SLA_VIOLATED`);
  2. resolution deadline passed → resolution breach;
  3. ≥ 75% of resolution time used → one `SLA_WARNING`;
  4. P1/P2 still waiting after the response deadline → escalate.
* Acknowledging or resolving late also records the breach immediately.
* `SlaState` (ON_TRACK, AT_RISK, BREACHED, MET) is shown in every incident response.
* Time comes from the injected `Clock`, so tests move time forward instead of waiting (see `SlaMonitorServiceTest`).

## 10. Security

| Requirement | How |
|---|---|
| Authentication | `POST /api/auth/login` → JWT token (HS256, 8 h). Every other request needs `Authorization: Bearer <token>`. |
| Password protection | BCrypt hashes (`SecurityConfig.passwordEncoder`); the hash is never returned by the API. Same error for "unknown user" and "wrong password" so attackers can't discover usernames. |
| Role-based authorization | The token carries the role. `@PreAuthorize("hasRole('ADMIN')")` on controllers. |
| Ownership rules | In `IncidentService`: only the *assigned* technician can work an incident; only the reporter can verify/close/give feedback; employees only see their own incidents. |
| Input validation | `@Valid` + annotations on request records; domain constructors validate again. Errors return 400 with per-field messages. |
| Secure API | Stateless (no sessions), CORS limited to configured frontend origins, secret from the `ITSM_JWT_SECRET` environment variable in production. |
| Concurrency | `@Version` on `Incident` (optimistic locking) stops two people overwriting each other → 409. |

Not built but worth mentioning in the report: HTTPS (handled by the hosting platform), rate limiting on
login, refresh tokens, account lock after repeated failures.

## 13. Exceptions

All extend `ItsmException`, which extends `RuntimeException` and declares `abstract HttpStatus getStatus()`.

| Exception | HTTP | When (brief's list) |
|---|---|---|
| `AuthenticationFailedException` | 401 | invalid login |
| `UnauthorizedOperationException` | 403 | unauthorized operation |
| `InvalidInputException` | 400 | invalid input / invalid incident |
| `InvalidStateTransitionException` | 409 | invalid state transition |
| `TechnicianUnavailableException` | 409 | technician unavailable |
| `WorkloadExceededException` | 409 | workload exceeded |
| `ResourceNotFoundException` | 404 | service / incident / user not found |
| `MissingSlaConfigurationException` | 500 | missing SLA config |
| `DuplicateResourceException` | 409 | duplicate username / service / category |
| Database failures (`DataIntegrityViolationException`, optimistic lock) | 409 | handled in `GlobalExceptionHandler` |

`GlobalExceptionHandler` turns every exception into the same JSON shape (`ApiError`): timestamp, status,
error, message, path, fieldErrors.

## 14. Spring words explained

| Word | Meaning |
|---|---|
| **Spring Boot** | A framework that starts a web server inside your Java program and wires your classes together. |
| **Bean** | An object Spring creates and manages (one per class marked `@Service`, `@Component`...). |
| **Dependency injection** | Instead of `new IncidentService(...)`, a class lists what it needs in its constructor and Spring passes them in. Makes testing and swapping parts easy. |
| `@RestController` | A class whose methods answer HTTP requests and return JSON. |
| `@GetMapping("/x")`, `@PostMapping` | Which URL and HTTP method a controller method handles. |
| `@RequestBody`, `@PathVariable`, `@RequestParam` | Where a parameter comes from: JSON body, `/incidents/{id}`, `?status=NEW`. |
| `@Valid` | Check the annotations (`@NotBlank`, `@Min`...) before the method runs. |
| `@Service`, `@Component` | "Spring, create one of these." |
| `@Transactional` | Everything inside runs as one database transaction: all saved or nothing. |
| `@Entity`, `@Id`, `@ManyToOne`, `@OneToMany` | JPA: map a class to a table and fields to columns/relations. |
| **JPA / Hibernate** | Saves and loads Java objects to/from the database for you. |
| **Spring Data repository** | An interface; Spring writes the implementation from method names. |
| `@PreAuthorize` | Role check before a method runs. |
| **JWT** | A signed string proving who you are; the server checks the signature instead of storing sessions. |
| **DTO** | "Data transfer object": the shape of JSON going in/out, separate from the entity. |
| `@Scheduled` | Run a method on a timer. |
| `@Value("${...}")` | Read a setting from `application.properties`. |

The brief wants at least three complete workflows. With the demo data, these work straight away
(in Swagger now, in the real UI once it exists).

**Workflow 1 – report, auto-prioritise, assign, notify**
1. Log in as `john`; `POST /api/incidents` for "Corporate Network" with "wifi keeps dropping", impact MEDIUM, urgency HIGH, 25 users.
2. Show the response: category NETWORK (auto), priority P2 with the explanation, SLA deadlines, assigned to alice.
3. Log in as `alice`; `GET /api/notifications` shows the assignment.

**Workflow 2 – investigate, SLA, resolve, verify**
1. As `alice`: acknowledge, start, add a note, request info.
2. As `john`: `info-response`.
3. As `alice`: `GET /similar` and `GET /suggested-resolutions`, then resolve.
4. As `john`: verify, close, feedback. Show `GET /api/incidents/{id}/audit` (full history).
5. As `admin`: `GET /api/reports/sla-risk` and `GET /api/reports/overview`.

**Workflow 3 – duplicates, correlation, escalation**
1. As `admin`: `GET /api/incidents` shows INC0004 flagged `potentialDuplicate` of INC0003.
2. `GET /api/reports/correlations` shows the Payment Gateway cluster.
3. Wait 5+ minutes without acknowledging INC0003 (P1): the SLA monitor escalates it and admins get
   "escalated" notifications. (`SlaMonitorServiceTest` proves the same thing instantly.)
4. Switch strategy: `PUT /api/admin/strategies/assignment {"name":"LOAD_BASED"}` and report another incident.
